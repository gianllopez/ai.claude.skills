# Complexity Tiers

A skill's folder structure should match its complexity — no more, no less. Adding `rules/` and a compiled `AGENTS.md` to a one-line procedure is overhead; cramming a large rule catalog into a single `SKILL.md` is unmaintainable. Pick the smallest tier that fits.

Only `SKILL.md` (with `name` + `description`) is required by the official spec. _Tiers 2_ and _3_ layer this collection's conventions on top, by complexity.

---

## Tier 1 · Minimal

Use when the skill is a single, stable instruction or procedure with no supporting assets, no executable helpers, and no need for versioning or a changelog. The whole thing fits comfortably in `SKILL.md` (keep the body under ~5k tokens).

```
<skill-name>/
└── SKILL.md
```

**Example:** `commit` — one procedure (analyze staged changes, write a _Conventional Commit_).

**Promote to Tier 2 when** you start wanting a helper script, reference docs, or version metadata.

---

## Tier 2 · Procedural

Use when the skill encodes a workflow or a tool/_API_ integration. It may bundle helper scripts (Level-3 executable code) or reference documents, and it benefits from version metadata and a human-facing `README.md`.

```
<skill-name>/
├── SKILL.md          # instructions + when-to-use
├── metadata.json     # version, author, abstract, references
├── README.md         # human-facing overview
├── scripts/          # optional: executable helpers (run via bash)
│   └── <tool>.py
└── references/       # optional: on-demand guides / schemas
    └── <topic>.md
```

**Examples:** `notion` (workflow over an _API_), `audit` (`scripts/audit.py` helper), and `skill-factory` itself (uses `references/` + `templates/`).

**Progressive disclosure:** move detail out of `SKILL.md` into `references/*.md` and let `SKILL.md` point to them, so they only load when needed. Prefer a `scripts/` helper over prose when an operation must be deterministic.

**Promote to Tier 3 when** the skill becomes a large catalog of many independent guidelines that you want to distribute as one compiled document.

---

## Tier 3 · Compiled (best-practices)

Use when the skill is a large, evolving set of many independent rules that (a) benefit from one-rule-per-file modularity and (b) are consumed as a single compiled artifact (`AGENTS.md`).

```
<skill-name>/
├── SKILL.md              # overview, when-to-apply, quick reference
├── metadata.json         # version, author, abstract, references
├── README.md             # human-facing overview + authoring workflow
├── rules/
│   ├── _sections.md      # index of all rules, grouped by section
│   ├── _template.md      # blank rule scaffold
│   └── <prefix>-<name>.md # one rule per file
└── AGENTS.md             # GENERATED: all rules compiled into one document
```

- Rule filenames use a category prefix (e.g. `arch-`, `conf-`) so they sort and group by concern
- `AGENTS.md` is a generated artifact — never hand-edited. It is regenerated by following the described procedure in `compilation.md` (reading the rules and `metadata.json`), not by any bundled script

**Examples:** `django-rest-framework-best-practices`, `react-native-with-expo-best-practices`.

---

## Decision heuristic

```
Is it one stable instruction with no assets?            → Tier 1
Is it one workflow/tool (maybe with a script)?          → Tier 2
Is it many independent rules → one compiled document?   → Tier 3
```

When in doubt, start one tier lower; promoting later is a copy-and-split, not a rewrite.
