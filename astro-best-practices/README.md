# Astro Best Practices

A structured repository of _Astro_ best practices, optimized for agents, LLMs, and human developers. The reference version is **Astro 7**.

## Structure

- `SKILL.md` - What the skill governs, when to apply it, and the quick reference
- `rules/` - Individual rule files (one per rule)
  - `_sections.md` - Index of all rules, grouped by section
  - `_template.md` - Template for creating new rules
  - `<prefix>-<name>.md` - Individual rule definitions
- `metadata.json` - Document metadata (version, author, abstract, reference links)
- `AGENTS.md` - Generated compiled output (all rules expanded). Never hand-edit

## Scope

This skill owns the framework and what it emits: rendering mode, island boundaries and hydration, the content model, the SEO system generated from it, assets, project structure, styling setup and build configuration.

Two things are deliberately excluded:

- **What happens inside a framework island.** A project rendering _React_ islands loads `react-core-best-practices` alongside this skill, which owns effects, state, the query layer, composition and typing. This skill owns only whether the island should exist and how it hydrates
- **Visual design direction and accessibility auditing.** Neither is verifiable against a diff, which is the bar every rule here meets. Semantic and structural guidance is justified on machine-readability and maintainability instead — the same call `react-best-practices` makes

## Using the Skill

Read `SKILL.md` for the overview and the quick reference, then the individual rule files for the full rationale and examples. `AGENTS.md` is the same content as one distributable document.

Every rule is written to be usable in both directions: the **Correct** block is what to write, and the **Incorrect** block is the defect to look for in a diff.

## Version Handling

_Astro_'s recent majors removed real APIs — `Astro.glob()`, legacy content collections, `<ViewTransitions />`, `@astrojs/db` — so guidance written against an older version does not merely age, it stops working. Two conventions keep this maintainable:

- Every rule that names a config key, import path or component states the version it belongs to
- Where a rule's intent outlives its API, the intent is stated first and the API second

When a new major ships, the rules to re-verify first are the ones whose examples contain configuration: `isl-static-by-default`, `content-collections-required`, `content-authoring-format`, `build-env-and-csp`, `build-logging` and `build-deployment-target`.

## Workflow

1. **Define rules:** create or edit markdown files in `rules/`
2. **Regenerate:** rebuild `AGENTS.md` from the rules (see below). It is a generated artifact — edit the rules, not `AGENTS.md`
3. **Format:** run `prettier --write` on each file that was modified
4. **Deploy:** distribute `AGENTS.md`

## Creating a New Rule

1. Copy `rules/_template.md` to `rules/<prefix>-<name>.md`
2. Choose the category prefix from the table above
3. Fill in the frontmatter (`title`, `impact`, `description`, `tags`)
4. Provide clear _Incorrect_ vs _Correct_ examples, and verify any API named in them against the current documentation
5. Register the rule in `rules/_sections.md` (section + order)
6. Regenerate `AGENTS.md`

## Regenerating `AGENTS.md`

There is no build script. `AGENTS.md` is regenerated by following the described procedure in `skill-factory/SKILL.md` (_AGENTS.md Compilation_) — reading `rules/`, `rules/_sections.md`, and `metadata.json`, then producing the compiled document. The sources of truth are the rules and `metadata.json`.
